# Recoder Engine Fusion Status

> Architecture-fusion map for the backend engine fleet. "Fusion" = an engine capability
> is consumed by a **product-flow service** (conductor / agent-os / memory / inference /
> governance / cloud / observability), reached on a real lifecycle seam. MCP-tool
> definitions, engine adapters, and tests are **not** fusion — they are surface, not wiring.
>
> **Status (2026-07-31):** The prioritized fusion backlog (P0–P6 + Waves 1–4 / C-series)
> is **COMPLETE**. All enumerated items shipped; every engine's write→read loop on a real
> product-flow lifecycle seam is closed (see §1 per-engine gap column). Three residual
> classes remain (kernel-export-blocked, owner-deferred, keep-dark-by-design); none are
> open fusion work — see §2.
>
> Thesis order (why each engine exists in the "total product"):
> beads = memory-for-all-agents · openfang = agentic-backend · pal = agent-comms-brain ·
> tensorzero = all-inference · governance = all-writes · mem0/colbert = full-recall ·
> recodergit = code-aware · ops-recorder = signals-feed · multica = squad-coordination ·
> browser-use = verify/research · ziti/xds = networking · dmux = multi-agent-layout.
>
> Fusion levels: **deeply-fused** (write+read on real lifecycle seams) ·
> **fully-fused** (entire loop closed, regression-locked) ·
> **partially-fused** (one half of the loop, or read-only) ·
> **adapter-only** (registered + MCP-exposed, zero product-flow consumer).

Truthful boundaries, not gaps — each is a capability with no product-flow consumer
by design (fuller detail in the §1 gap column):

- **tensorzero** — per-principal attribution for substrate-level CLI metering
  (currently a stable conductor service subject); the residual of item 8.
- **pal** — `debate` / `escalate` on the `engines.pal()` facet are unconsumed by
  design (no faked consumer); `pal.route` / `pal.models` / `clink` / `thinkdeep` /
  sidecar tools stay agent-facing MCP affordances over the same transport.
- **mem0** — `get` / `getAll` / `update` / `history` have no product-flow consumer;
  `delete` stays soft (reviewable-memory model); the OSS entity `graph_store` is
  intentionally unconfigured.
- **colbert** — `/score` (RRF) + `/rerank/batch` throughput niceties have no
  consumer; `server.py /api/search` is superseded by `rerank_server.py` (left in
  place, OSS-dir no-prune).
- **ops-recorder** — the write server's read tools (`.list` / `.get`) stay
  unregistered; `.handoff` is deferred (no product consumer); `disposition()` writes
  the TS Postgres repo but does not `PATCH` the sidecar `/status` (round-trip
  asymmetry, backlog).
- **multica** — `SquadService.isEligible` stays always-true; a live agent-online
  eligibility probe is deferred, never fabricated.
- **recodergit** — the `completion-hook.adapter.ts:153` repoId-derivation divergence;
  and there is no *autonomous* conductor PR-auto-review flow (the `github.pr_review`
  MCP tool is the only trigger).
- **tmux / dmux** — box-wide introspect (`list-windows` / `capture-pane` / …) and the
  `dmux <repoPath>` attach command stay MCP-only and gated to the single-tenant
  desktop composition; the shared tmux server has no tenant partition key, so no
  shared/prod product read model consumes them.

None of the above is open *fusion* work: A is kernel-export-gated, B is one env flip
away and owner-gated, and C is deliberate KEEP-DARK. Every engine's write→read loop
on a real product-flow lifecycle seam is closed (see §1).
