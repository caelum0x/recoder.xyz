# Build log — 2026-10-24

## Round 2: openfang async seam — DONE (backlog item #9)

The known, documented blocker: `backend/src/domains/engines/openfang-runtime.ts`'s
own header comment (and `docs/RECODER-ARCHITECTURE.md`'s "PARKED — openfang Hands
lifecycle" entry) explicitly called out that the openfang-napi `run_agent` call was
"SYNCHRONOUS AND BLOCKING (Rust `block_on`) — it holds the Node event loop for the
full agent turn." That's not a cosmetic issue: openfang agent turns are real LLM
calls (seconds to minutes), and every `#[napi]` method on the SAME engine handle —
health checks, other agents' reads/writes, every other IPC call in the whole
process — queues behind it for the full duration. The same `block_on` pattern was
duplicated across 7 more methods (`compact_session`, `reload_extension_mcps`,
`reconnect_extension_mcp`, `load_workflows_from_dir`, `register_workflow`,
`run_workflow`, `publish_event`).

Fixed the root cause instead of papering over it: enabled napi-rs's `async`
feature (`napi = { version = "3", features = ["napi4", "async"] }` in
`backend/engines/rust/openfang/Cargo.toml`) and converted all 8 methods in
`crates/openfang-napi/src/lib.rs` from `pub fn foo(&self) -> String` with
`self.rt.block_on(...)` to genuine `pub async fn foo(&self) -> String` with a
plain `.await` on a cloned `Arc<OpenFangKernel>`. napi-rs's own `#[napi] async fn`
support means the call now returns a real JS `Promise` immediately and the native
future runs on napi's own worker pool — never holding the addon's calling thread.
Removed the now-dead manual `tokio::runtime::Runtime` field + `Builder` (napi's
async feature manages its own runtime).

Propagated the signature change through the whole TS call chain so nothing is
silently awaiting a Promise-shaped string or vice versa:
- `backend/src/domains/engines/openfang-native.ts` — the 8 methods are now typed
  `Promise<string>` on `OpenfangEngineInstance`, each annotated with why.
- `backend/src/domains/engines/adapters/napi/openfang-napi.adapter.ts` — the
  `ENGINE_OPS` dispatch table's value type widened to `string | Promise<string>`
  and `invoke()` now `await`s the call (a no-op for the sync ops, a real await for
  the 8 async ones) — every op's call site stays identical.
- `backend/src/domains/engines/openfang-runtime.ts` — `launchOpenfangRun` now
  `await`s `engine.runAgent(...)`; header comment corrected (was documenting the
  blocking behavior as an "accepted precedent").
- `backend/src/domains/engines/openfang-workflow.ts` — `OpenfangWorkflowDriver`'s
  `register`/`run`/`registerAndRun` are now real `async` functions returning
  `Promise<...>` (they call `registerWorkflow`/`runWorkflow`, two of the 8
  converted ops); updated the matching unit tests in
  `openfang-workflow.test.ts` to `await` them (mock fns changed from sync to
  `async`, same assertions). `packages/agent-workflows/src/native-workflow.ts`'s
  consumer port already declared `Promise<NativeWorkflowRunResult> |
  NativeWorkflowRunResult`, so it needed no change — it was already
  forward-compatible with an async driver.
- `docs/RECODER-ARCHITECTURE.md` — updated the "PARKED — openfang Hands
  lifecycle" entry: the async-seam reason is now resolved (with evidence); the
  OTHER original reason (`ConductorRuntimeId` being a closed subprocess-CLI
  union) still parks the Hands-lifecycle wiring itself — left truthfully PARKED,
  not marked done, since actually wiring it is separate follow-up work.

**Verified by actually running it, not by adding test files**: built the real
debug `.node` (`cargo build -p openfang-napi`, copied the cdylib to
`openfang_napi.node`) and ran a throwaway Node script (deleted after the run)
against the COMPILED addon directly:
- every one of the 8 converted methods (`runAgent`, `compactSession`,
  `reloadExtensionMcps`, `reconnectExtensionMcp`, `loadWorkflowsFromDir`,
  `registerWorkflow`, `runWorkflow`, `publishEvent`) returns a real
  `instanceof Promise` value, not a string — the architectural change is real at
  the FFI boundary, not just in the Rust source;
- a `setInterval` tick counter scheduled BEFORE firing all 7 single-call async
  ops (without awaiting) had already ticked 10-15 times by the time the ops'
  promises were even inspected, proving the event loop was never blocked while
  they were in flight (the old `block_on` code would have starved this timer for
  the full native-call duration);
- every promise resolved to parseable, correct JSON — including the real
  degrade-safe error paths (`"Agent not found: <uuid>"` for a nonexistent agent
  id on `runAgent`/`compactSession`, `"No MCP config..."` for
  `reconnectExtensionMcp`, schema-validation errors for malformed
  `registerWorkflow`/`publishEvent` JSON);
- the composite `registerWorkflow` → `runWorkflow` chain (a real, schema-valid
  workflow) completed end-to-end through the new async path, returning
  `{ok:true, run_id, output}`.

Also ran: `cargo build -p openfang-napi` and `cargo test -p openfang-napi` (both
