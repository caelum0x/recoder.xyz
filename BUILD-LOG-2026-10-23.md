### 4. Railyard Mint usage-sink emitter — DONE (backlog item #11)

ARCHITECTURE.md's own owner-decision section names this the lowest-risk Railyard adoption ("a pure
additional emit target... alongside the MoR subscription... low risk"), but flags the broader
Railyard adoption question as needing owner sign-off since it touches billing. Built the adapter in
a way that is genuinely zero-risk to the existing checkout path and inert until an owner provisions
real Railyard Mint credentials:

- `backend/src/domains/billing/ports/usage-sink.port.ts` — a NEW, narrow port, deliberately separate
  from the frozen `BillingProviderPort` (Phase 9 MoR contract) so a metering rollup service can never
  become eligible for `BILLING_PROVIDER` selection.
- `backend/src/domains/billing/providers/railyard-mint/railyard-mint.sink.ts` — real HTTP forwarder
  (reuses the domain's existing `providerFetch` helper) that POSTs the same `MeterEvent` batch the
  MoR provider receives to `POST {baseUrl}/v1/usage/events`, Bearer-authenticated. Degrade-safe: no
  `RAILYARD_MINT_BASE_URL`/`RAILYARD_MINT_API_KEY` configured ⇒ `emitUsage` is a truthful no-op and
  `health()` reports `degraded`/`configured:false` — never a fabricated push.
- `backend/src/domains/billing/services/metering.service.ts` — added an optional `extraSinks` list to
  `MeteringServiceDeps`; `flushOnce` now fans the same drained batch out to every sink in parallel via
  `Promise.allSettled`, logging (not throwing) per-sink failures. A sink's failure/latency can never
  delay or block the primary MoR provider's `emitUsage`/`markFlushed` decision — verified below.
- `backend/src/domains/billing/config.ts` + `backend/src/bootstrap/config.ts` — new
  `RAILYARD_MINT_BASE_URL` / `RAILYARD_MINT_API_KEY` / `RAILYARD_MINT_PRODUCT_ID` env vars, read once
  at bootstrap (per ARCHITECTURE §10.8: no `process.env` in domain code) into a new `railyardMint`
  config slice.
- `backend/src/domains/billing/billing-module.ts` — wires the sink into `createMeteringService` only
  when `RAILYARD_MINT_API_KEY` is present; absent ⇒ `extraSinks` is omitted entirely ⇒ byte-identical
  behavior to before this adapter existed.

**Verified by actually running it**, not by adding test files: a throwaway script (deleted after the
run) spun up a real local HTTP server, pointed a configured sink at it, and confirmed (a) the
unconfigured sink no-ops and reports `degraded` health, (b) the configured sink actually POSTs the
correct wire JSON (`product_id`/`subject_id`/`kind`/`quantity`/`idempotency_key`/`occurred_at`) with
the correct `Authorization: Bearer` header, (c) `health()` reports `up` against a real 200, and (d) a
deliberately-failing extra sink wired into `createMeteringService.flushOnce()` still lets the primary
fake MoR provider's `emitUsage`/`markFlushed` complete normally (sink failure only logs). Also ran the
full `backend` `tsc --noEmit` (clean, 0 errors) and the existing
`src/domains/billing/__tests__/metering-quota.service.test.ts` suite via `vitest run` (22/22 pass,
unchanged).
